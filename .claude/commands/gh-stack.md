# gh-stack

Use when several branches form a parent-to-child chain and the user wants a GitHub stack, not just independent PRs. Follow the user's requested operation; do not create PRs or push branches just because they asked to inspect a stack.

**Prerequisite:** Before using this command, verify the GitHub CLI and GitHub Stacks extension are installed by running `gh --version` and `gh stack --help`. If either command is unavailable, stop and tell the user what is missing. Do not install anything unless asked. For read-only requests, use `gh stack view --json` only after this check.

**Before any stack mutation, ask for explicit confirmation of the specific operation and target branches/remote, even if the user requested it.** This includes `gh stack init`, `add`, `modify`, `rebase`, `sync`, `push`, `submit`, `link`, `merge`, and `unstack`. Read-only inspection needs no confirmation. If a planned operation fails and a different mutation is needed, explain the change and ask again before proceeding. When a task requires commits, commit each change on the appropriate branch in the stack, and follow the `commit-push` skill/command for commit-message conventions and confirmation before pushing. For any user yes/no decision, use the available `ask_user` skill or equivalent interactive question tool rather than treating ambiguous text as approval.

1. Run `gh stack <subcommand> --help` before using it. Identify the repo, trunk, branch chain, and target remote with `git remote -v`, `git log --oneline --graph --all`, and `gh stack view --json`. Do not assume `origin` is upstream. Check `git status --short` before any operation that can rebase or push; preserve unrelated changes and worktrees.
2. For a new stack, `gh stack init BOTTOM BRANCH2 [MORE]` can adopt existing branches in bottom-to-top order. To extend an **existing** stack, do not re-run `init` with its tracked branches; it fails with `branch "BOTTOM" already exists in a stack`. Check out the current top/parent with `gh stack checkout PARENT`, then run `gh stack add CHILD`. `add` adopts an existing child branch when its history is based on the parent, or creates it if absent; verify with `gh stack view --json`. Do not stage or commit unrelated changes.
3. To publish the stack and create/update its PRs when requested, use `gh stack submit --auto --remote REMOTE` for non-interactive submission (new PRs default to draft; use `--open` only if requested). It pushes branches, sets each PR's base to its parent, and creates/updates the GitHub stack. Check `--help` for interactive/auto/draft behavior and confirm PR creation with the user if they only asked to push. If existing PRs are up to date, `submit` can leave them unchanged and append only the new child's PR to the existing remote stack. `gh stack push --remote REMOTE` only pushes branches; it does NOT create PRs or guarantee a UI-visible stack.
4. If PRs already exist but the GitHub UI does not show a stack, check them with `gh pr view NUMBER --repo OWNER/REPO --json state,baseRefName,headRefName,url`. Local `gh stack view` is not proof of remote linkage. Link existing open PRs bottom to top with `gh stack link BOTTOM_PR NEXT_PR [MORE_PRS] --remote REMOTE`. Prefer PR numbers to avoid branch pushes. Verify the command reports a created/updated stack and report its number.
5. If a PR was closed because its head branch was deleted, verify PR state, `git ls-remote --heads REMOTE BRANCH`, and `git rev-parse BRANCH`. With authorization, restore the branch using `git push REMOTE BRANCH:BRANCH`, then `gh pr reopen NUMBER --repo OWNER/REPO`; retry the requested stack operation. Do not force-push or recreate a PR before checking whether it can be reopened.
6. When a parent branch gets a new commit, descendants may need cascading rebases and their PR bases must follow. Check `gh stack view --json` for `needsRebase`; run `gh stack rebase --help`, then ask before running `gh stack rebase` (which rebases the stack from parent to child). Resolve conflicts, stage only the resolved files, and continue with `gh stack rebase --continue`. Then ask before `gh stack submit --auto --remote REMOTE` to publish/sync the rewritten descendants and PR bases. Verify each PR head/base with `gh pr view NUMBER --repo OWNER/REPO --json headRefOid,baseRefName,headRefName,url` and confirm `gh stack view --json` shows no `needsRebase`.
7. If a direct `git push` succeeds but GitHub's PR head appears stale, verify the remote branch SHA with `git ls-remote --heads REMOTE BRANCH` and the PR via `gh pr view`. Do not assume a successful push updated PR metadata or run unrelated operations blindly. For stack branches, use the approved `gh stack submit --auto --remote REMOTE` sync path, then recheck PR heads and bases. If the parent commit changed, follow the cascading rebase procedure above. Never force-push without explicit authorization.
8. If `gh stack push` reports `stale info`, compare local and remote commits with `git rev-parse BRANCH` and `git ls-remote --heads REMOTE BRANCH`. Distinguish an absent branch from an already-matching branch. Do not force-push an already-matching branch. `gh stack sync` and `gh stack rebase` can rewrite history: use only when needed, in a clean worktree, and do not force-push without authorization.

Finish by checking PR bases/states and remote stack linkage, not only local tracking. Report the branch/PR order and any remaining mismatch.
